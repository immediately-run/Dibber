Dibber
How it works For agents Spec GitHub

Your to-do list belongs in your repo.

Dibber keeps tickets as plain Markdown files next to your code. Your coding agent reads them, works them and closes them, and you review every change in the same pull request.

Paste this into Claude Code, Codex, opencode or Antigravity:

Set up Dibber ticket tracking in this repo by following https://immediately-run.github.io/dibber/

Or in a terminal: npx -y @immediately-run/dibber init

Free and open source · No account · No server · Nothing to host

A ticket is just a file.

my-app/
├─ src/
├─ tickets/
│  ├─ APP-1.md  done
│  ├─ APP-2.md  in progress
│  └─ APP-3.md  ready
└─ .dibber/config.json
tickets/APP-3.md---
id: APP-3
title: "APP-3 — Add a dark mode toggle"
status: available
depends_on: [APP-2]
---

### Why
Reading at night hurts.

### Exit criteria
- [ ] a test: the toggle switches the theme
- [ ] a test: the choice survives a reload

GitHub renders it. Your editor opens it. Your agent greps it. Nothing to host, nothing to lose.

File it. Work it. Close it.

  1. 1

    File it

    “Add a dark mode toggle.”

    Your agent writes tickets/APP-3.md: what, why, and checks that prove it’s done.

  2. 2

    Work it

    “What’s next? Go.”

    It picks the next ready ticket, builds it, and runs the checks.

  3. 3

    Close it

    “Ship it.”

    The ticket says status: done and stays put, so the code can link back to why it exists.

Why files?

No lock-in

Tickets live in git with your code. Clone the repo and you have the tracker.

Reviewed with the code

A ticket change is a diff in the same pull request as the work.

Links that last

Closing a ticket never moves it, so links from code, commits and PRs keep working.

Written down

The format is a short spec with a JSON Schema and a test suite. The tool is optional.

Just you and your agent? That’s all you need. Several agents or a team? Add Baton for real claims. Your tickets stay the same.

Why “Dibber”?

In orienteering, a dibber is the chip you punch at every checkpoint, so the course remembers where you’ve been. A Dibber ticket does the same for your work.

It’s also how you call dibs.

For coding agents

If a person asked you to set up Dibber in their repository, do this. People: this is exactly what your agent will do.

  1. Check that Node.js 18 or later is installed (node --version). If it isn't, tell the person and stop.
  2. Pick a short upper-case ticket prefix from the repository's name, such as APP for my-app. Ask the person only if there's no obvious one.
  3. Run npx -y @immediately-run/dibber init --yes --prefix APP, using your prefix. It adds tickets/, .dibber/config.json, an AGENTS.md section, and three skills in .agents/skills/ and .claude/skills/. It never overwrites a file.
  4. Run npx -y @immediately-run/dibber check. It must report no problems.
  5. Tell the person what was added, and commit it when they agree. The skills load in your next session.
  6. Ask what they'd like to work on first, and file it as their first ticket.

The same steps as Markdown: docs/install.md. The whole project for agents: llms.txt.
